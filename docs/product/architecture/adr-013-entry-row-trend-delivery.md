# ADR-013: Entry-Row Trend Delivery — One Day-Keyed Projection, One Row Definition, Raw Read Untouched

## Status

Accepted (2026-09-09, Propose mode; feature `numeric-trend-history`, US-016). Does not supersede any prior ADR; relies on ADR-004 (the series is the source of the number), ADR-005 (pure core), ADR-006 (injected read-only pure callable), ADR-010 (route-level projection of the read `GET /` already performs).

## Context

The smoothed trend exists as a **number** exactly once — the glance line, for the most recent entry day — and as a **shape** everywhere else. "How much has the trend moved since mid-August?" is a subtraction of two numbers, and the product answers it by asking the user to read pixels off a curve whose y-axis was deliberately widened by ADR-012 so that small movements look small. DISCUSS locked the product shape (D6–D12): both entries lists — the front page's last-7 (`#recent-entries`) and the History page's complete record (`#history-entries`) — become aligned `Date | Raw | Trend` tables; the trend value is the existing full-record smoothed series read at each entry's own day (derived, never stored); both lists change together because one row grammar serves them; a failing trend empties the trend cells and nothing else.

Three things were left open for this ADR:

- **Which series, delivered how.** The number must be the *same* value the chart plots and the glance reports (A36) — one algorithm, one rounding path, or the same day reads differently on two surfaces of one screen.
- **The wire.** Three renderers need a row: `GET /` and `GET /graph` render server-side, and the client repaints the recent list in place from the `POST /entries` response after a save (D-19). `entry_wire_pair` is today the single `{date, weight_kg}` shape shared by that hand-back and `GET /entries` (the raw lens's data source). Extending it reaches both; extending only the hand-back risks a second place a trend can come from.
- **Degradation.** The glance already degrades to an absent line without touching the save (D-13). The lists need the same containment, scoped to the trend cells alone, on a surface where the raw values must survive.

Constraints binding every option: one series (G-3, ADR-004), read-only ports gain no methods (ADR-005 / CLAUDE.md), derived never stored (no schema change), zero added fetches/scripts/taps on `/` and ≤2 s interactive (KPI-1, G-2/G-5), no telemetry from a render (ADR-009), one row grammar across both surfaces (the ADR-008 parity principle applied to markup), and exactly one `all_entries()` read per page.

## Decision

**One pure day-keyed projection in the core; one row definition in the shell; the raw read untouched.**

- `core/trend.py` — `trend_by_day(entries) -> dict[date, float]`, built from the shipped `trend_series`: `{point.day: point.trend_kg for point in trend_series(entries)}`. Total, clock-free, order-invariant. Because the grid spans first→last entry day, it is defined at **every** entry day, so a row can never want for a value. It lands in `trend.py` rather than a new module: a day-keyed view of the trend series is the same concern as the series, unlike ADR-012's axis rule, which was not.
- It is injected at the composition root as a **third read-only pure callable**, `TrendByDayProjection = Callable[[Sequence[Entry]], Mapping[date, float]]`, beside `trend_series_in` and `glance_summary_of` (ADR-006's precedent). `ports.py` is untouched — this is a driving-side callable, not a port protocol, and no read-only port gains a method.
- `web/routes.py` gains **one row definition**: frozen `EntryRow(day_text, raw_text, trend_text)` built by `entry_row(day, weight_kg, trend_kg | None)`, at two named precisions — `RAW_DECIMALS = 1` (the scale's own resolution) and `TREND_DECIMALS = 2` (a derived value with real resolution below 0.1, and a damped filter that often moves only ~0.05 kg across a week). The glance keeps its ADR-006 single decimal and states the same value. `recent_entry_rows` and `complete_record_rows` both map over it; the single-string `entry_row_text` is retired with its grammar. Templates place cells into `<td>`s and format nothing.
- **Degradation is one shell function returning an empty mapping**: `trend_by_day_or_degrade(entries)` logs `trend.rows.degraded` and returns `{}`. The row builder holds **no degrade branch** — it looks a day up with `.get(day)` and renders an empty cell on a miss — so "a failing trend empties the trend cells and nothing else" is structural, not conventional, and the impossible-by-construction missing day is covered by the same path.
- **Wire**: `entry_wire_pair` stays the pure `{date, weight_kg}` base shape and remains its single definition; `recent_entries_payload` — the one call site feeding the list repaint — extends each pair with an additive, always-present, nullable `trend_kg`. **`GET /entries` is untouched.** It is the raw lens's data source; the trend lens has `GET /trend`. Putting smoothed values there would give the chart two paths to one series, and would run a full Kalman+RTS pass on every raw-lens fetch for a consumer that discards it.
- **Markup**: `<table>` on the two existing ids, keeping the existing `aria-label`, with one `<thead>` row of `<th scope="col">Date / Raw (kg) / Trend (kg)</th>` and one `<tr>` of three `<td>` per entry. `kg` appears once per column header, never per cell. `theme.css` moves its two `li` rules to `th`/`td` rules on the same selectors, right-aligning the numeric columns on tabular figures.
- **Precision was retuned by the first real render, not by taste** (DISCUSS OQ-15, closed at DELIVER). Shipping both columns at 0.1 kg was the pinned default; on a genuine month of ~0.04 kg/day decline the smoothed trend moved 0.05 kg across the front page's seven rows, so every row printed `77.5` and the column read frozen while the curve visibly sloped — exactly the falsifier OQ-15 named. The trend column now renders at 0.01 kg. The raw column stays at 0.1 kg because the scale never measured a second digit, and inventing one would be the dishonesty this product exists to avoid.
- **Day wording gets one definition**: `core/types.py: day_label(day)`. `Saved.confirmation` and `entry_row` both call it; the confirmation's output is byte-identical, guarded at DoD.

Falsifiable at the HTTP boundary and on the page: for a record whose newest entry day smooths to 77.48 kg, the glance line reads `Trend: 77.5 kg`, the top row's trend cell reads `77.48`, and the same day on `/graph` reads `77.48` — every one of them checked against the series rather than against another rendering, so a re-rounding of an already-rounded number cannot pass by looking self-consistent; a save's response carries `recent[i].trend_kg` equal to the value rendered for that row; `GET /entries` and `GET /trend` are byte-identical to pre-feature.

## Alternatives Considered

- **`trend_kg` on `entry_wire_pair` itself, reaching `GET /entries` too**: Rejected. It is the one-line change and it keeps a single wire shape, but it publishes smoothed values on the raw-lens endpoint where nothing consumes them, gives the chart two routes to one series (the drift A36 forbids), and turns a pure windowed filter into a full-record smoothing on every raw fetch. What D-18 protects — the server-rendered recent list and the save's hand-back telling the same story — is preserved by both reading the **same mapping** in the same request, not by the wire shape.
- **Handing back pre-formatted row strings instead of numbers**: Rejected. It would remove the client's formatting entirely, which is attractive, but `mergedRecord` reads `weight_kg` out of `recent` to keep the ADR-010 prefill map fresh after a save. The numbers must stay; formatting the cells client-side from the same grammar is the smaller cost.
- **Storing a trend column on `entries`**: Rejected outright. ADR-004 makes the series a pure function of the full entry set, revised retrospectively by the RTS pass; a stored column would be stale the moment any day is backfilled (`js-3-maintain`), and would need a migration to hold a number that costs microseconds to derive.
- **A new port method (`TrendProjection.trend_at(day)` or `.trend_by_day()`)**: Rejected. Read-only ports gain no methods (CLAUDE.md / ADR-005), and per-row lookup would be n smoothings for n rows — n chances to disagree with the chart.
- **A new core module (`core/rows.py`) for the projection**: Rejected. ADR-012 earned `core/axis.py` because an axis rule is a distinct concern with its own tunable constants; this projection has no constants and is a view of the series it sits beside. Splitting it would put two names for one concept in two files.
- **Keeping `<ul>` and faking columns with CSS**: Rejected. Two columns of numbers under headers are tabular data; a list would announce "Fri 24 Jul 82.2 77.2" as one run-on string to a screen reader and would need a new utility class for the visually-hidden headers, which ADR-007 forbids.
- **A Raw/Trend toggle over the lists instead of two columns**: Rejected by the user at DISCUSS (D6). Hiding one number to read the other defeats the comparison the feature exists for.

## Consequences

- Positive: one algorithm and one rounding path, so a day's trend value is the same on the glance line, both lists and the chart — the sharpest claim in the feature and a directly testable one; the row grammar has one definition serving three renderers; the projection and the row builder are pure and fall inside the per-feature mutation gate; `GET /entries` and `GET /trend` stay byte-identical, so every shipped chart AT is untouched; no port, adapter, route, dependency, origin, event, probe or migration changes; degradation needs no branch anywhere in the row path; the extracted `day_label` removes a pre-existing duplicate of the day wording.
- Negative / disclosed: the two columns now speak different precisions, which reads as an inconsistency until one knows that only one of the two numbers was ever measured; the glance line and the top row show the same value with a different number of digits, so the equality that matters is checked against the series rather than between renderings; the save response's `recent` pairs are no longer the same shape as `GET /entries`'s entries — a deliberate asymmetry, documented here because it will look like an oversight to a future reader; the retrospective revision of past rows after a backfill (ADR-004, intended) is now **visible as digits** and will read as instability to anyone who has not met the smoother; the row grammar change moves three test modules and two CSS rules that pinned the old single-string row, all enumerated in the feature delta; `/` is pre-cached by the service worker, so the change forces a `SHELL_CACHE` bump (`-v5 → -v6`); the History page now runs a full-record smoothing on render, which it did not before (an O(n) scalar fold, microseconds at the record's scale, and the same pass `/trend` already performs on every chart fetch).
