## Feature Summary and Business Context

**US-013 + US-014 — the record becomes self-maintainable.** The entry screen gained a native `<input type="date">` above the weight field, prefilled and bounded to the device-local day, so a forgotten Sunday can be backfilled and a fat-fingered 88.4 can be corrected *where the habit already lives* — no admin surface, no edit mode, no separate flow. Job `track-true-weight-trend`, moment `js-3-maintain` (*"I notice I forgot to log yesterday or mistyped a value three days ago"*) — the last journey moment still without a UI. **No new job-story moment**: the backend has honored dated saves since `weight-trend-tracker` (any non-future date, one-per-day upsert); this feature closed the gap by surfacing the date. Selecting a stored day prefills its value with an editing hint, an empty day says so plainly, and after every save the picker returns to today so habit-typing can never clobber a past day.

The KPI story is again structural. A backfill session is inherently slow — open the picker, recall, read the prefill — and a single one would poison the weekly median that KPI-1's 5-second target guards. So **repairs are classified at write time and carry no morning timing at all**: `entry_ms` is recorded NULL, which rides the shipped null-skip for 0 samples, and the same classification stamps `"backdated": true` for the new KPI-8 repair counter. One `{date}` row and one `entry.saved` event per save stayed pinned. Same discipline as graph-first-home's ambient/deliberate KPI-3 split, one wave later.

## Key Decisions

- **DISCUSS (D6–D8, user-locked; A20–A24)**: D6 native `<input type="date">`, always visible, prefilled today — zero extra taps on the default morning, keypad covering it on open explicitly accepted; no picker library. D7 edit prefill — a stored day fills the field and names its value, so an edit is never blind. D8 post-save reset to today, because the common combo is *backfill yesterday, then log today*. A21 pinned one hint line (anchor / editing / no-entry, never stacked); A23 pinned KPI-1 purity as a hard requirement (0 samples) with the mechanism left to DESIGN; A24 pinned prefill correctness for **any** stored day, not just recent ones.
- **DESIGN (D-21–D-26, ADR-010/011)**: **D-21** prefill = the shipped 4-entry `recent_weights_map` widened to a **whole-record `{iso_day: kg}` map rendered inline** — a pure projection of the `all_entries()` read `GET /` already performs, so one client map answers both the anchor and the prefill, synchronously, at ~5.6 KB/yr. Rejected: lazy `GET /entries?scale=ALL` (async race, wrong-then-right hint flicker on a trust-building feature, and the headline AC unobservable in a browser-less suite); bounded window (fails A24 outright). **D-22** backdated classification **at write time from the phone's claimed day** — the save message gains one additive optional `today` field, the same claim `?today=` already carries on reads; classification runs *after* validation via a pure core pair; a garbled or absent claim falls back to server UTC and **never** blocks or 400s a save. Rejected: client-omission convention — a purity rule resting on the client omitting a field is one no acceptance test can falsify. **D-23** KPI-8 = a payload flag plus a new `backdated_saves_since` query, not a second event name, keeping `WeightLogging`'s effect universe at one row + one event. **D-24** one `#entry-hint` node, three states, pure `hintFor` — "never two hints" is *structural*. **D-25/D-26** `min` = first entry day − 1 year (a UX assist against a mistyped year, which would otherwise stretch every trend recompute to ~3,650 grid points); zero port-protocol changes, read-only ports gain **no methods at all**.
- **DISTILL**: 13 scenarios / 14 executions on `milestone-10-dated-entry.feature`, error-edge share ≈42%; RED gate **9 MISSING_FUNCTIONALITY / 5 GREEN-preserved / 0 BROKEN**, zero production scaffolds (every RED anchor is an HTTP-observable absence). The high preserved count is the honest signature of a presentation delta on a shipped backend. Four inherited-AT touchpoints renegotiated out loud — including one **found at DISTILL and absent from DESIGN's list**: `seed_timed_week` seeded a whole week in a single instant, which under write-time classification is indistinguishable from seven repairs and would have stripped six of seven timings out of the KPI-1 report. The helper now walks the clock, because a morning *is* a same-day save.

## Lessons Learned

1. **Mutation testing and adversarial review are not substitutes — they found different things on the same code.** The reviewer returned **zero findings** after explicitly attacking KPI-1 purity and hostile device-day input; the mutation run then found that the suite had never put the device clock and the server clock on *different days during a save* — a gap on this feature's own headline invariant (a phone one timezone ahead saves for ITS today while the server is still on yesterday; ADR-011 says that is a morning, and the surviving mutant called it a repair, silently costing the morning its KPI-1 sample). Review reasons about the code that exists; mutation reasons about the tests that don't. Keep both gates, and keep them independent.
2. **Three survivors, one axis, one scenario pair.** Two of the three survivors were the same inversion at the same site (`framed is None` → `is not None` and its `AddNot` twin), and the third — a save dated exactly at the forward skew boundary — was the same untested axis seen from the save side rather than the read side. `device-day-frame.feature` had always exercised that boundary on READS. Triage survivors by *axis*, not by count: three findings collapsed to one missing scenario pair, closed with **zero production change and zero new step definitions** (every Given/When/Then already existed; the divergence was composed at the HTTP boundary from two independent inputs — `composition.device_day` feeding the payload's claim while `FakeClock` held the Background's day). The gate had already passed at 96.5%; closing the axis anyway was the right call precisely because it *was* the headline invariant.
3. **An SSOT file in a machine-readable format needs a parse check in the wave that edits it.** Two product YAML files — `kpi-contracts.yaml` and `outcomes/registry.yaml` — stopped parsing under the DISTILL delta, because three prose scalars embedded a `key: value` fragment (`` `backdated: true` ``, `{iso_day: kg}`, `"backdated": true`) that YAML reads as a nested mapping indicator. Both load at the pre-feature HEAD. It survived DISTILL and all of DELIVER undetected and was found at finalize, for the uncomfortable reason that **nothing consumes them**: `kpi-contracts.yaml` is referenced only in a pytest marker description, and the outcomes CLI has been broken upstream since OUT-7. Fixed here as folded block scalars with zero wording change. The absence of a consumer is exactly why the defect persisted — a format chosen for machine-readability that no machine reads is prose with extra punctuation, and it drifts silently. A `yaml.safe_load` sweep over `docs/product/` belongs in CI.
4. **A shell-cache bump is triggered by a changed pre-cached RESPONSE, not by a new asset.** DESIGN's Component Decomposition wrote `sw.js` UNCHANGED with the reasoning *"no new asset ⇒ no APP_SHELL change, no cache bump"*. True for the first half, wrong for the second: `APP_SHELL` pre-caches `/` itself, and `/` grew a date row, so without a new `SHELL_CACHE` name an offline open would have kept serving the pre-date-row entry screen out of `-v3`. Caught by the platform reviewer, accepted as a DELIVER pre-requisite, shipped as `-v4` with the asset list genuinely untouched. The inventory-table phrasing reasons over the asset list alone and will under-call this again — the trigger to write down is the response, not the file.
